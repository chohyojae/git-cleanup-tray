# Windows 성능 비교 계획

Git 명령을 동시에 실행하는 방식과 멀티스레드 라이브러리 처리를 비교합니다. Windows 실측은 아직 하지 않았습니다. 이번 구현과 자동 테스트는 macOS에서 진행했습니다.

## 이번 구현의 macOS 참고 측정

`cargo run --release --example scan_benchmark`로 다시 실행할 수 있습니다. [측정 코드](../../examples/scan_benchmark.rs)는 사용자 저장소를 사용하지 않고, 커밋 1개인 임시 저장소 16개를 만듭니다. 저장소마다 로컬 원격 HEAD가 있는 상태에서 같은 검사를 순차 또는 4개씩 동시에 실행했습니다.

macOS 27.2 Apple Silicon, Apple Git 2.54.0, release 빌드에서 준비 실행 5회 후 각각 30회를 번갈아 측정한 결과입니다. 이미 파일 캐시가 사용되는 반복 실행이며 저장소 생성 시간은 제외했습니다.

| 실행 방식 | 16개 전체 완료 p50 | 전체 완료 p95 |
|---|---|---|
| 순차 Git 실행 | 971.83ms | 1021.58ms |
| Git 명령 4개 저장소 동시 실행 | 273.30ms | 288.98ms |

이 측정은 작은 저장소의 검사 시간만 확인한 것입니다. Windows 속도, 대형 저장소의 디스크 경합, 메모리, 라이브러리의 성능을 뜻하지 않습니다. 아래 Windows 비교와 메모리 측정은 별도로 진행합니다.

## 실행 조건을 맞춥니다

| 비교 대상 | 실행 방식 | 용도 |
|---|---|---|
| 순차 Git 실행 | 저장소 하나씩 Git 명령 실행 | 동시 실행 자체의 개선을 확인할 참고값 |
| 동시 Git 실행 | 이번에 구현한 저장소별 동시 검사 | 라이브러리 전환을 평가할 주 비교 대상 |
| A안: `gix` | 같은 수의 스레드에서 같은 저장소 조회 | 동시 Git 실행 대비 추가 개선 확인 |
| B안: `git2` | A안과 같은 스레드 수·조회 범위 | 두 라이브러리 비교 |

동시 작업 수를 1·2·4개로 맞춰 비교하고, 제품 기본값은 CPU 수에 따라 2~4개로 둡니다. 앱의 저장소별 스레드와 라이브러리 내부 병렬화는 구분합니다. 먼저 내부 병렬화를 끄고 비교한 뒤 필요하면 별도 결과를 냅니다. 순차 Git 실행과 멀티스레드 라이브러리만 비교해 전환 효과를 과장하지 않습니다.

`Scan All` 전체 완료 시간뿐 아니라 개별 Scan이 실행 중일 때 다른 저장소를 요청한 경우도 측정합니다. 요청 접수·실제 시작·각 저장소 완료·전체 완료 시간을 기록하고, 동시 실행 상한 때문에 생긴 대기 시간을 구분합니다. 같은 저장소의 중복 요청이 추가 작업을 만들지 않는지도 확인합니다.

Windows 11 x64와 ARM64에서 각각 실행합니다. ARM64는 해당 아키텍처용 앱·Git을 사용하고 x64 에뮬레이션은 별도 결과로 표시합니다. macOS Apple Silicon은 회귀 확인용으로 같은 시나리오를 실행합니다.

## 테스트 저장소

실제 사용자 저장소에서 정리하지 않습니다. 기존 통합 테스트를 바탕으로 임시 저장소를 만들고 Git 전역·시스템 설정과 분리합니다.

| 저장소 구성 | 커밋 / 로컬 브랜치 / custom ref / 연결된 워크트리 | 확인할 비용 |
|---|---|---|
| 작은 저장소 | 100 / 10 / 10 / 0 | Git 시작과 라이브러리 초기화 |
| ref가 많은 저장소 | 10,000 / 1,000 / 1,000 / 0 | ref 일괄 조회, 병합 판정, 반복 재검사 |
| 워크트리가 많은 저장소 | 1,000 / 50 / 50 / 20 | 목록·인덱스·파일 검사. 변경 없음·변경 있음·잠금 상태 혼합 |
| 파일이 많은 저장소 | 1,000 / 20 / 20 / 5, 워크트리당 추적 파일 50,000개 | 파일 순회·인덱스. 추적하지 않는 폴더와 무시된 빌드 산출물도 포함 |
| 저장소 여러 개 | 작은 저장소 20개, 크기가 다른 저장소 혼합 | 일괄 완료 시간, 개별 검사 응답, CPU·디스크 경합, 작업 후 메모리 |

수치는 생성 목표입니다. 같은 OID와 여러 이력에 흩어진 ref, fast-forward·머지 커밋·별도 이력을 포함합니다. 저장소는 Git 명령으로 구성하고 `.git` 파일을 직접 만들지 않습니다. 생성 시간과 생성용 Git 실행은 측정에서 제외합니다. 정리는 매번 같은 상태의 저장소를 새로 준비해 실행합니다.

공백·한글 경로를 기본으로 쓰고 Windows 긴 경로·대소문자는 별도로 검사합니다. 앱 화면 없이 같은 코어 함수를 실행하는 측정과, 실제 화면에서 여러 Scan을 요청하는 측정을 나눕니다.

## 시간·프로세스 수

`ProcessGitRunner::run()`을 감싸 명령 종류별 횟수·시간을 수집하고, 전체 작업 시간은 `Instant`로 따로 잽니다. 전체 인자·경로·ref·원격 URL은 기록하지 않습니다.

- 검사·정리·최신화·전체 주기 작업을 분리합니다. 정리는 삭제 직전 재검사와 실제 삭제 시간을 나눕니다.
- 저장소별 시간과 전체 완료 시간을 모두 보고합니다. 동시에 실행한 명령의 소요 시간을 합한 값은 전체 경과 시간과 다릅니다.
- `git --version` 같은 작은 명령의 반복 실행은 시작 비용 참고치로만 사용합니다. Git 초기화도 포함되므로 순수 프로세스 생성 시간이라고 부르지 않습니다.
- 라이브러리도 저장소 열기·ref 조회·커밋 관계·파일 검사 시간을 나눕니다. Git 호출 수와 보조 프로그램 실행 수는 따로 셉니다.
- Windows Performance Recorder/Analyzer 또는 Process Monitor로 실제 하위 프로세스를 확인합니다. Git 인증·필터·SSH 보조 프로그램도 포함합니다.
- 네트워크 없는 검사는 기준 브랜치를 직접 지정하거나 로컬 원격 HEAD를 사용합니다. 라이브러리 로컬 조회의 Git 실행 목표는 0회이며 보조 프로그램이 필요한 결과는 구분합니다.
- 최신화는 로컬 원격 저장소와 실제 네트워크를 분리합니다. 인증·전송 대기로 로컬 처리 속도를 판단하지 않습니다.

같은 장비·SSD·전원 모드·Git 버전·빌드 설정을 사용하고 실행 순서를 번갈아 배치합니다. Windows Defender 등 운영 보안 설정을 유지하고 상태를 적습니다. 저장소별 fsmonitor·untracked cache·commit-graph·pack·필터 설정도 같게 맞춥니다.

준비 실행 5회 후 30회 이상 반복해 중앙값(p50)과 느린 쪽 95백분위(p95), 원본 표본을 보관합니다. 첫 실행·새 앱 프로세스·같은 프로세스 반복 실행을 나눕니다. 새 프로세스도 OS 파일 캐시가 비었다는 뜻은 아니므로, 별도로 확인한 경우에만 캐시가 비어 있는 실행으로 표기합니다.

## 메모리·크기·대기 상태

1. 창을 열지 않은 트레이 대기 상태의 CPU·메모리를 기록합니다.
2. 작업 중 최대 메모리와 마지막 스레드 종료 후 같은 시간을 기다린 메모리를 기록합니다. 동시 작업 수에 따른 총 메모리도 비교합니다.
3. 50회 반복 후 대기 상태의 누적 증가를 확인합니다. 화면 생성 비용은 별도 측정합니다.
4. Windows는 Private Bytes·Working Set, macOS는 profiling 빌드의 physical footprint를 사용합니다. 다른 지표의 MB를 직접 비교하지 않습니다.
5. 같은 release 설정에서 실행 파일·함께 배포할 C 라이브러리 크기, 전체 의존성 수, 빌드 시간을 비교합니다. `cargo tree -e features` 결과도 보관합니다.

macOS 기존 참고값은 `AGENTS.md`의 트레이 대기 메모리 14.1MB입니다. 현재 동시 Git 실행 방식도 다시 측정해 비교합니다. 저장소 객체를 해제해도 메모리 할당기·메모리 매핑 때문에 OS 측정값이 즉시 돌아온다고 가정하지 않습니다.

## 라이브러리 채택 기준

다음 수치는 실측 전 제안입니다. 비교 기준은 **같은 동시 실행 수의 Git 명령 방식**입니다.

- 안전·동작 비교가 모두 통과해야 합니다. 삭제 대상 증가나 상태 불명 항목을 변경 없음으로 보는 차이는 허용하지 않습니다.
- ref가 많은 여러 저장소의 전체 검사 p50이 동시 Git 실행 대비 30% 이상 줄어야 합니다. Git 실행 횟수 감소도 확인합니다.
- 작은 저장소·파일이 많은 저장소의 개별 및 전체 검사 p95가 10% 넘게 느려지면 원인을 해결하거나 해당 조회를 Git 명령으로 유지합니다.
- 정리·최신화는 조회 시간 감소와 전체 시간 감소를 따로 보고합니다. 삭제 명령이 여전히 큰 비용일 때 C안을 검토합니다.
- 대기 중 반복 확인이나 상주 작업 스레드로 CPU 사용이 늘지 않아야 합니다. 작업 후 메모리가 기준보다 `max(2MiB, 10%)` 이상 늘면 원인 해결 또는 설계 근거가 필요합니다.
- 세 플랫폼에서 같은 안전 조건을 만족해야 합니다. Windows ARM64는 교차 빌드 성공만으로 실행 검증을 대신하지 않습니다.
