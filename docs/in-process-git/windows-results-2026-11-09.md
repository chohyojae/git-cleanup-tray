# Windows x64에서 Git 명령과 gix 조회 비교

2026-11-09, `feature/in-process-git-proposals`. `a0f7014`의 두 조회 구현을 **같은 release 예제·입력·저장소 동시 실행 수**로 비교했습니다. 앱 코어는 변경하지 않았으며, Windows에서 예제를 실행할 수 있도록 테스트 공용 경로 처리와 예제의 결과 비교를 수정했습니다. [macOS 결과](macos-results-2026-11-09.md)와 같은 네 구성을 사용합니다.

같은 동시 실행 수 4개 기준으로 전체 Scan p50이 구성에 따라 **79.0~98.1% 줄었습니다.** 720개 기록 표본과 준비 실행 모두 계획이 일치했고 조회 오류는 없었습니다.

## 전체 Scan 시간

아래는 해당 구성의 **모든 저장소가 끝난 시간(ms)**이며 개별 저장소 하나의 시간이 아닙니다. 정렬한 30개 표본의 nearest-rank로 p50·p95를 계산했고, 단축률은 같은 동시 실행 수의 p50끼리 비교했습니다. [시간 원본 CSV](benchmarks/windows-x64-2026-11-09.csv)의 24개 그룹마다 반복 번호 1~30이 한 번씩 있는지, 저장소 수·Git 호출 수·유효한 양수 시간이 기록됐는지도 확인했습니다.

| 구성 | 동시 실행 수 | Git 명령 p50 / p95 | gix p50 / p95 | p50 단축 |
|---|---:|---:|---:|---:|
| small | 1 | 16224.15 / 23550.47 | 709.55 / 2115.66 | 95.6% |
| small | 2 | 5706.54 / 8285.39 | 162.53 / 273.62 | 97.2% |
| small | 4 | 4973.00 / 8597.55 | 96.87 / 180.22 | 98.1% |
| refs | 1 | 5721.45 / 6815.82 | 1797.97 / 3090.91 | 68.6% |
| refs | 2 | 3674.06 / 7962.96 | 1215.47 / 4899.87 | 66.9% |
| refs | 4 | 2749.80 / 3911.89 | 577.99 / 1595.67 | 79.0% |
| worktrees | 1 | 10425.31 / 13114.20 | 728.18 / 1515.75 | 93.0% |
| worktrees | 2 | 7846.35 / 13400.50 | 567.71 / 1356.90 | 92.8% |
| worktrees | 4 | 7751.71 / 8482.30 | 427.92 / 783.80 | 94.5% |
| files | 1 | 4843.92 / 15598.77 | 309.74 / 1949.18 | 93.6% |
| files | 2 | 3827.86 / 6479.53 | 321.56 / 1365.37 | 91.6% |
| files | 4 | 5728.12 / 7924.58 | 530.01 / 931.36 | 90.7% |

측정 중 `GitRunner::run` 호출은 전체 Scan 한 번당 small 96회, refs 48회, worktrees 80회, files 28회였고 gix는 네 구성 모두 **0회**였습니다. 저장소 생성·기준 계획 생성·준비 실행은 이 횟수에서 제외합니다. OS 전체의 프로세스 추적 결과는 아니며, Git 자체가 만드는 보조 프로세스도 별도로 세지 않았습니다.

모든 조건에서 같은 동시 실행 수의 gix p50·p95가 Git 명령보다 짧았습니다. 파일 구성은 두 방식 모두 동시 실행 4개의 p50이 2개보다 길었습니다. 동시 실행 수는 1·2·4 순서로 측정했고 일부 표본의 변동도 컸으므로, 이번 결과만으로 동시 실행 수의 효과나 지연 원인을 단정하지 않습니다. 주 비교는 같은 동시 실행 수에서 번갈아 실행한 두 조회 방식입니다. 안티바이러스·CPU·디스크의 비용을 분리한 프로파일링은 수행하지 않았습니다.

## 작업 후 메모리와 대기 CPU

같은 Rust 측정 코드를 구성·방식마다 새 프로세스로 실행했습니다. 동시 실행 4개, 준비 5회 뒤 worktrees·files는 각각 30회, files는 추가로 각각 50회 반복했습니다. 30회는 원래 예제, 파일 50회는 같은 코드의 메모리 전용 진입점과 외부에서 준비한 입력을 사용합니다. [측정 스크립트](benchmarks/measure-windows-memory.ps1)는 전체 Scan·계획 비교와 작업 스레드 회수가 끝난 대기 신호를 감지한 뒤 5초 후 Private Bytes와 Working Set을 한 번 읽고, 다음 5초 동안 해당 프로세스의 CPU 시간 증가를 기록합니다. [메모리·CPU 원본 CSV](benchmarks/windows-x64-memory-2026-11-09.csv)에 실제 관측 지연·CPU 구간 길이·전체 스레드 수도 남겼습니다.

초기 files 30회는 대량 임시 파일 정리가 오래 걸려 PowerShell 정리를 지원했습니다. commands는 완료 표본·생성 시각·폴더 구조로 소유를 확인한 폴더를 정리한 뒤 관측했고, gix는 전용 임시 부모 폴더의 정리가 지연돼 완료 신호 후 약 13분이 지나 별도로 관측했습니다. 두 프로세스 모두 작업을 끝낸 대기 상태였지만 정리 절차와 관측 시점이 달라 **files 30회는 참고값이며 두 방식의 차이를 계산하지 않습니다.** 파일 구성의 주 비교는 같은 준비 입력을 읽는 50회 결과입니다. 워크트리 구성의 두 방식은 모두 기존 Rust 정리를 사용했습니다.

원본의 `fixture_cleanup`으로 정리 절차를 구분합니다. `cleanup_ms`는 확인한 PowerShell 정리 구간만 기록하며 전체 Rust 정리 시간은 아닙니다. `ready_signal_age_ms`는 별도로 관측한 files/gix 30회의 완료 신호부터 관측까지 약 777,895ms였음을 남깁니다. 이 표본의 `observed_delay_ms`는 별도 관측을 시작한 뒤 기다린 약 5초이므로 완료 신호 직후 5초로 해석하면 안 됩니다. `after_scan_ms`의 빈칸은 해당 간격을 기록하지 않았다는 뜻입니다. 관측값은 모두 프로세스가 살아 있는 동안 읽었습니다.

파일 50회는 준비·정리 비용이 관측 프로세스에 섞이지 않도록 [준비 도구](benchmarks/prepare-windows-files.ps1)로 저장소 네 개를 한 번 만들고 두 방식이 재사용합니다. 커밋 3개, 데이터 파일 10,000개·이력 파일 1개, clean 연결 워크트리 1개라는 논리 상태는 원래 files 구성과 같습니다. 파일 생성과 인덱스 구성·검증은 외부에서 수행합니다. 두 방식 모두 새 프로세스에서 같은 경로를 읽으며 전체 계획 비교도 유지합니다. 이 입력은 관측 프로세스가 삭제하지 않고 두 실행 종료 후 소유 표식을 확인해 정리합니다. `fixture_cleanup=shared-fixture`로 구분합니다.

메모리는 bytes를 1,048,576으로 나눈 MiB로 표시합니다. 원본의 peak Working Set은 해당 프로세스 안에서 수행한 준비·계획 검증을 포함한 전체 최고값이며 Git 하위 프로세스는 포함하지 않습니다. 파일 50회의 저장소 생성은 별도 프로세스라 peak에 포함되지 않습니다. Scan만의 최대 메모리로 해석하지 않았습니다.

| 구성·반복 | Git 명령 Private / Working Set, MiB | gix Private / Working Set, MiB | Private 차이, MiB |
|---|---:|---:|---:|
| worktrees, 30회 | 5.06 / 9.37 | 6.04 / 11.52 | +0.98 |
| files, 30회 | 4.36 / 7.65 | 10.67 / 12.05 | 비교 제외 |
| files, 50회 | 4.78 / 9.37 | 9.87 / 13.04 | +5.09 |

같은 입력을 사용한 파일 50회에서 gix의 작업 후 Private Bytes는 Git 명령보다 약 5.09MiB 많았습니다. 여섯 표본 모두 약 5초의 대기 구간 동안 해당 프로세스의 CPU 시간 증가는 0ms였습니다. 관측 시 전체 스레드 수는 파일 50회에서 Git 명령 2개·gix 4개였고 나머지 네 표본은 1개였습니다. 전체 스레드 수를 기록한 값이며 스레드별 역할이나 이후 수명은 추적하지 않았습니다.

이 값은 UI 없는 코어 예제의 작업 후 메모리이며 실제 tray 앱의 idle 메모리가 아닙니다. 30회와 50회는 프로세스와 fixture 준비·정리 절차가 달라 이 값으로 장기 누적 증가나 메모리 누수를 판정할 수 없습니다. macOS physical footprint와 Windows Private Bytes·Working Set도 서로 다른 지표입니다.

## Windows 실행을 위한 수정과 검증

기존 테스트 공용 코드의 `std::fs::canonicalize()`가 Windows 임시 경로에 `\\?\` 접두사를 붙였습니다. Git for Windows의 `clone --bare`가 이 경로의 `HEAD`를 만들지 못해 저장소 구성 단계에서 실패했습니다. [공용 fixture](../../tests/common/mod.rs)를 기존 의존성의 `gix::path::realpath()`로 바꿔 macOS의 `/var` 별칭 해소를 유지하면서 일반 Windows 경로를 사용하도록 했습니다. 새로운 의존성이나 앱 동작 변경은 없습니다.

또한 예제가 계획 전체의 Debug 문자열을 비교하면서 Windows의 `/`와 `\` 구분자 차이를 결과 불일치로 처리했습니다. 저장소 순서·ID·경로·기준 커밋·후보·제외 사유를 타입으로 비교하고 양쪽 오류가 비어 있는지 확인하도록 바꿨습니다. 후보 안의 경로도 `Path` 비교를 사용하며, 비교는 기존과 같이 시간 측정에서 제외합니다.

| 검사 | 결과 |
|---|---|
| `cargo fmt --check` | 통과 |
| `cargo clippy --all-targets -- -D warnings` | 통과 |
| `cargo test` | 105개 통과. 빈 전역 Git 설정·시스템 설정 비활성화 상태의 일반 Windows 환경 |
| `GIT_CLEANUP_TEST_READS=gix`로 정리·기준 브랜치·안전·경합·최신화 테스트 | 42개 통과 |
| `cargo build --release --example scan_benchmark --example scan_memory_benchmark --bin git-cleanup-tray` | 최종 소스 통과 |
| 메모리 전용 release 진입점 | 통과. 원래 예제와 같은 측정 함수 사용 |
| 두 예제의 준비 입력 검증 테스트 | 각 2개 통과. 입력 디렉터리 미삭제와 잘못된 저장소 수 거부 |
| PowerShell 문법·소유 범위 검증 | 통과. 소유 표식 불일치 삭제·fixture 밖 Git 명령 거부, 소유한 임시 폴더 정리 확인 |

의존성을 변경하지 않아 이번 작업에서는 `cargo deny check`를 다시 실행하지 않았습니다. 이전 검사 기록은 [macOS 보고서](macos-results-2026-11-09.md)에 있습니다.

## 재현과 남은 범위

[Windows 실행 절차](windows-benchmark.md)에 시간 비교 명령과 [메모리 측정 스크립트](benchmarks/measure-windows-memory.ps1) 사용법이 있습니다. 저장소 루트에서 release 예제를 빌드한 뒤 실행합니다.

이 장비에서 `--case all --warmups 5 --iterations 30` 시간 비교 명령은 약 64분 걸렸습니다. 저장소 생성·정리까지 포함한 전체 명령의 경과 시간이며, 위 표의 Scan 측정 범위와 다릅니다. `--case refs --parallelism 4`처럼 구성과 동시 실행 수를 지정해 필요한 조건만 다시 측정할 수도 있습니다.

이번 결과는 Windows x64 장비 한 대의 코어 Scan 비교입니다. Windows ARM64, 실제 tray의 작업 후 메모리·idle CPU, UI에서 개별 요청을 겹쳐 넣는 응답, 삭제·최신화 전체 시간, 더 큰 저장소, 긴 경로·대소문자·파일 잠금·복잡한 CRLF/attributes 조합, shallow·alternates, git2 비교는 추가 확인 범위입니다. OS 전체의 하위 프로세스 추적과 전환 전후 Windows 배포 크기 비교도 포함하지 않았습니다.
