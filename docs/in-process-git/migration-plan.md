# 동시 검사와 라이브러리 전환 계획

## 먼저 적용한 동시 검사

기존에는 일괄 검사가 한 스레드에서 저장소를 차례로 처리했고, 앱도 작업 하나만 허용했습니다. 이번 브랜치에서는 두 제한을 바꿨습니다.

- 개별 Scan과 Scan All이 저장소별 대기 목록을 공유합니다. CPU 수에 따라 기본 2~4개까지 동시에 검사하고, 완료 이벤트가 오면 다음 저장소를 시작합니다.
- 실행·대기 중인 같은 저장소는 중복으로 넣지 않습니다. 등록 시 같은 common Git directory를 하나로 합치는 기존 정책을 유지합니다.
- 검사 결과는 완료한 저장소부터 화면에 반영합니다. 일괄 검사 함수의 반환값은 완료 순서와 관계없이 입력 순서를 유지합니다.
- 취소하면 새 검사를 시작하지 않고 진행 중인 검사를 회수합니다. 종료 시에도 실행 중인 스레드를 회수합니다. 한 저장소의 오류나 스레드 생성 실패가 나머지 검사를 막지 않습니다.
- 삭제·최신화·설정 저장과 검사 사이의 기존 제한은 유지합니다. 정리는 저장소 순서대로 실행하며 확인 대기 중에는 새 검사를 받지 않습니다.
- 일할 때만 스레드를 만들고, 작업이 없으면 스레드·반복 타이머를 남기지 않습니다. 기존 주기 작업 타이머는 마지막 검사가 끝난 뒤 재개합니다.

구현은 [app/scans.rs](../../src/app/scans.rs), [jobs/queue.rs](../../src/jobs/queue.rs), [jobs/batch.rs](../../src/jobs/batch.rs)에 있습니다. 동시 검사 수를 무제한 늘리는 것이 목표는 아닙니다. Git 프로세스와 디스크 접근이 몰리지 않도록 상한을 공유합니다.

## 라이브러리를 연결할 위치

라이브러리 실험도 위 작업 관리를 사용합니다. 저장소를 실행하는 순서·동시 실행 수는 같게 두고, 실제 조회를 담당하는 부분만 바꿉니다.

```text
화면 → 앱 → 저장소별 작업 관리 → 정리 계획 생성
                                  ├─ Git 명령 조회 → GitRunner → guard → git 실행 파일
                                  └─ 라이브러리 조회 → 작업 스레드 안의 저장소 객체

삭제·최신화 → 기존 GitRunner → guard → git 실행 파일
```

현재 `GitRunner`는 명령 인자와 Git 출력 형식을 사용합니다. 라이브러리 결과를 Git 출력 문자열로 만들었다가 다시 파싱하면 명령 해석과 복사 비용이 남습니다. `git/` 안에 작업의 의미를 표현하는 조회 인터페이스를 추가하고, 기존 타입으로 결과를 반환하도록 제안합니다. 아래 타입과 인터페이스 전환은 아직 구현하지 않았습니다.

| 조회 작업 | 반환할 앱 타입 | 유지할 동작 |
|---|---|---|
| 저장소 식별 | `RepositoryIdentity` | 메인·연결 워크트리의 공통 Git 디렉터리 판정, bare 저장소 거부 |
| 기준 브랜치 판별 | symbolic ref 대상, full ref와 `ObjectId` | 사용자 지정 → 로컬 원격 HEAD → 허용된 네트워크 질의 순서, 로컬 기준 브랜치 우선 |
| ref 목록·병합 여부 | `RefEntry`와 판정 결과 | 일반·symbolic ref와 실제 object 종류 구분. tag가 가리키는 커밋만 보고 일반 커밋 ref로 분류하지 않음 |
| 커밋 관계 | `Result<bool>` | 같은 OID, 다른 이력, 누락 object, shallow 저장소에서 기존 Git 판정과 일치 |
| 워크트리 목록 | `WorktreeEntry` | 메인·등록·detached·잠금·경로 누락·오류 구분 |
| 파일 변경 여부 | `Result<bool>` | 스테이징·작업 파일·추적하지 않는 파일·서브모듈 검사. 오류를 변경 없음으로 처리하지 않음 |

라이브러리 타입은 `git/` 밖에 노출하지 않고 `ObjectId`, `BaseRef`, `RepositoryId`를 유지합니다. 오류는 `CleanupError`의 기존 분류로 변환하며, 부족하면 작업 종류와 원인을 담는 variant를 추가합니다. Git 표준 오류나 종료 코드를 임의로 만들지 않습니다.

라이브러리의 저장소 객체는 각 작업 스레드 안에서 열고 닫습니다. `gix::Repository`는 기본적으로 `Sync`가 아니며 빌드 기능에 따라 `Send` 조건도 달라집니다. 여러 저장소의 객체를 하나로 공유하지 않고, 라이브러리 내부 병렬화까지 켜서 동시 실행 수가 곱절로 늘지 않게 합니다. [스레드 제약](https://docs.rs/gix/0.90.0/gix/struct.Repository.html)

## 다음 작업 순서

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| 0. 동시 Git 검사 | 이번 브랜치에서 구현. 개별·일괄 Scan의 공유 상한, 중복 방지, 완료·취소 처리 | 실제 Git 동시 조회와 작업 관리 테스트, 형식·정적 검사·전체 테스트·release 빌드 확인 |
| 1. 기준 측정 | 순차 Git 실행, 동시 Git 실행, 같은 스레드 수의 `gix`·`git2` 실험 비교 | Windows x64·ARM64에서 시간·메모리·프로세스 수 확인 |
| 2. 조회 인터페이스 | 먼저 기존 Git 명령 조회를 연결. 허용 범위를 `PLAN.md`와 `AGENTS.md`에 반영 | 기존 결과와 안전 정책 유지 |
| 3. ref·커밋 관계 | 저장소 식별, 기준 브랜치의 로컬 정보, ref 목록과 병합 판정을 라이브러리로 교체 | 같은 OID·누락 object 등에서 결과 일치, 제한된 캐시로 성능 확인 |
| 4. 워크트리·파일 검사 | 각각 별도 변경으로 전환 | 잠금·경로·파일 변경 판정 일치, 검사 중 파일 쓰기 없음 |
| 5. 실행 직전 조회 | 정리·최신화 직전의 반복 조회 전환. 삭제·최신화 명령은 유지 | 대상별 최신 상태 확인과 경합 테스트 통과 |
| 6. 기본값 전환 | 검증된 라이브러리 조회 사용. 미지원 저장소는 Git 명령으로 조회 | [같은 동시 실행 조건의 성능 기준](windows-benchmark.md)과 세 플랫폼 검증 통과 |
| 7. 라이브러리 삭제 검토 | C안의 작업별 변경 API, 조건부 ref 변경, 일부만 성공한 결과 설계 | 별도 정책 개정과 안전 검증. 앞 단계만으로 삭제 API를 허용하지 않음 |

검사 방식이 바뀌어도 최신화 실패 저장소를 해당 주기 정리에서 제외하는 정책은 유지합니다. 라이브러리 도입을 이유로 시작 시 자동 검사를 켜거나 큰 결과를 상주시켜 두지 않습니다.

## 캐시와 삭제 직전 확인

1. 검사 시작 시 기준 커밋을 고정하고 ref·object 종류를 읽습니다. 보호 정책은 현재 계획 생성 코드가 담당합니다. 커밋 그래프·압축 데이터 캐시는 저장소마다 상한을 정하고 처리 중에만 사용합니다. 동시 작업 수만큼 메모리가 늘어나는지도 확인합니다.
2. 검사 도중에도 외부 Git 작업이 상태를 바꿀 수 있습니다. 검사 결과가 변경 권한을 뜻하지 않으며, 정리 직전에 다시 확인합니다.
3. 확인 창에는 기존 `CleanupPlan`만 전달합니다. 저장소 객체·인덱스·메모리 매핑·그래프는 작업 스레드가 끝나기 전에 해제합니다.
4. 정리 시 새 조회 상태를 열고 기준 ref와 판별 근거를 다시 확인합니다. 대상마다 ref·symbolic 여부·워크트리 연결·잠금·파일 변경을 새로 읽습니다. 라이브러리의 갱신 보장이 불명확하면 객체를 다시 엽니다.
5. 삭제 뒤 다음 검사에 이전 ref·인덱스·설정을 쓰지 않습니다. 바뀌지 않는 OID의 object 캐시와 변경 가능한 정보의 캐시는 구분합니다. 외부 Git의 잠금 파일을 제거하지 않습니다.
6. `git branch -d`, `git worktree remove`, 이전 OID를 지정한 `git update-ref --no-deref -d`를 유지합니다. 상태가 달라졌으면 `StateChanged`로 건너뜁니다.

Git 명령도 모든 경합을 원자적으로 막지는 않습니다. `git branch -d`는 검사 당시 OID를 삭제 조건으로 받지 않습니다. 현재 보호를 낮추지 않으면서 이 틈을 줄이는 방법은 C안에서 검증합니다. 조건부 ref 변경만으로 파일 변경이나 다른 워크트리의 체크아웃 경합까지 해결했다고 보지 않습니다.

## 라이브러리가 지원하지 않는 경우

저장소를 열 때 object 형식, ref 저장 방식, 확장 기능, 워크트리 설정을 확인합니다. SHA-256, reftable, shallow/partial clone, alternates, sparse index, 필터·설정 조합은 테스트로 확인한 범위만 지원합니다.

- 명확한 기능 미지원이면 해당 저장소의 조회 단계를 처음부터 Git 명령으로 다시 수행합니다. 서로 다른 시점의 일부 결과를 합치지 않습니다.
- 권한 오류, 손상된 ref·인덱스·object, 파일 변경, 잠금은 미지원과 구분합니다. 실패를 병합 완료나 변경 없음으로 처리하지 않습니다.
- 실행 직전 조회를 Git 명령으로 바꾸면 해당 대상의 안전 검사도 처음부터 다시 합니다. 앞서 성공한 삭제를 다시 실행하지 않습니다.
- 개발·테스트 단계에서 조회 방식을 선택해 비교합니다. 기본 전환 후에도 Git 명령으로 복귀할 수 있게 하되 설정 저장 형식 변경은 별도로 정합니다. 사용자가 지정한 Git 실행 파일 경로를 유지합니다.
- 원격 HEAD 질의는 `allow_remote_query`를 따릅니다. 저장소를 여는 것만으로 fetch나 누락 object 다운로드를 시작하지 않도록 확인합니다.

## 검증할 내용

기존 실제 Git 테스트 저장소를 두 조회 방식에 사용합니다. 결과의 행 순서·상세 오류 문구는 정규화하되, 후보 OID·기준 판별 출처·제외 이유·오류 유무는 비교합니다. 다른 삭제 후보가 생기면 기본 전환을 중단합니다.

| 테스트 | 확인할 내용 |
|---|---|
| 작업 관리·일괄 검사 | 개별 요청과 Scan All의 공유 상한, 같은 저장소 중복 방지, 먼저 끝난 자리 재사용, 대기 취소, 스레드 생성 실패·검사 오류 격리 |
| 저장소·기준 브랜치 | 임의 이름, 사용자 지정, 로컬 symbolic HEAD, 오프라인, 연결 워크트리 중복 등록, 공백·한글·긴 경로 |
| 정리 안전 조건 | 같은 OID, 병합 여부, tag/tree/blob, symbolic ref, 보호 namespace, 메인·등록·detached·경로 누락·잠금 워크트리 |
| 파일 변경 검사 | 스테이징·작업 파일·추적하지 않는 폴더·무시된 파일·충돌·서브모듈·권한 오류·sparse index·필터, `status.showUntrackedFiles=no` |
| 경합·금지 명령 | 검사 후 ref·기준·원격 HEAD·파일·잠금 변경, 일반 ref의 symbolic 전환. 기존 guard 유지와 검사 중 라이브러리 쓰기 금지 |
| 최신화·주기 작업 | 앞선·갈라진 이력 보존, 체크아웃 경합, fetch 목적지 제한, 태그 갱신·prune 금지, 진행 중 작업 보호, 실패 저장소 정리 제외 |

검사 전후 ref·인덱스·설정·워크트리 정보의 내용과 수정 시각을 비교해 자동 인덱스 저장도 없는지 확인합니다. 테스트는 전역·시스템 Git 설정과 격리하며 Git 관련 테스트에 공백·한글 경로를 포함합니다.

각 변경에서 `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`를 실행합니다. 의존성 변경 시 `cargo deny check`, 성능·크기 변경 시 `cargo build --release`와 실측을 추가합니다. 빌드 기능·lockfile·C 라이브러리 의존성도 결과에 남깁니다.
