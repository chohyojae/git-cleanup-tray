# Windows Git 처리 속도 개선

작성일: 2026-11-08. 기존 코드 검토 기준: `44785b2`.

## 먼저 무엇을 비교하나요?

**여러 저장소에서 Git 명령을 동시에 실행하는 방식과, 같은 수의 스레드에서 Git 라이브러리를 호출하는 방식을 비교합니다.** 순차 실행을 없애는 효과와 라이브러리로 바꾸는 효과를 따로 확인해야 합니다.

이 문서에서 사용하는 두 방식은 다음과 같습니다.

- **Git 명령 실행**: 앱이 설치된 `git` 실행 파일을 별도 프로세스로 실행합니다. Windows에서는 `git.exe`를 실행하는 방식이며, Git CLI라고 부르는 기능입니다.
- **라이브러리 내부 처리(인프로세스)**: 앱이 `gix`나 `git2`의 Rust 함수를 호출합니다. 해당 작업을 위해 Git 실행 파일을 새로 시작하지 않습니다.

검사(Scan)는 삭제할 수 있는 항목을 찾는 작업이고, 정리(Clean)는 확인한 항목을 실제로 삭제하는 작업입니다.

## 이번 브랜치에서 구현한 내용

현재 Git 명령 실행 방식에 저장소별 동시 검사를 적용했습니다. 라이브러리 도입은 아직 검토 단계입니다.

- `Scan All`은 사용 중인 저장소들을 동시에 검사합니다. CPU 수를 기준으로 기본 2~4개까지 실행하고, 나머지는 대기합니다.
- 개별 `Scan`도 같은 대기 목록을 사용합니다. 다른 저장소가 검사 중이어도 요청할 수 있고, 여유가 있으면 바로 시작합니다. `Scan All` 안에서만 동시 실행되는 구조가 아닙니다.
- 같은 저장소의 중복 요청은 받지 않습니다. 각 저장소는 `검사 중` 또는 `대기 중` 상태를 표시하고, 먼저 끝난 저장소부터 결과를 갱신합니다.
- 취소하면 아직 시작하지 않은 검사는 버리고 실행 중인 검사는 마무리합니다. 작업이 없을 때 스레드를 남겨 두거나 주기적으로 확인하지 않습니다.
- 삭제·최신화·설정 저장과 검사가 겹치지 않도록 변경 작업은 기존 제한을 유지합니다. 정리 실행은 저장소 순서대로 처리합니다.

구현 위치는 [저장소별 검사 관리](../../src/app/scans.rs), [공유 대기 목록](../../src/jobs/queue.rs), [일괄 검사](../../src/jobs/batch.rs)입니다.

[측정 예제](../../examples/scan_benchmark.rs)로 순차·동시 Git 검사를 비교할 수 있습니다. 이번 macOS 참고 결과는 [측정 문서](windows-benchmark.md)에 기록했으며 Windows 실측과 라이브러리 비교는 아직 남아 있습니다.

## 라이브러리를 사용한다면 어떤 안이 좋나요?

**A안을 먼저 실험하고 B안과 비교하는 것을 추천합니다.** 두 안 모두 위와 같은 저장소별 동시 실행 구조를 사용합니다.

| 제안 | 라이브러리로 처리할 작업 | Git 명령을 계속 실행할 작업 | 선택 기준 |
|---|---|---|---|
| A. 조회는 `gix`, 삭제와 최신화는 Git 명령 | 저장소·브랜치·ref·워크트리 조회, 병합 여부와 파일 변경 검사 | 삭제, 오래된 워크트리 정보 정리, fetch, fast-forward, 원격 HEAD 질의 | 우선 실험할 안. Rust로 구현하고 캐시 수명을 관리하기 좋습니다 |
| B. 조회는 `git2`, 삭제와 최신화는 Git 명령 | A안과 같은 범위 | A안과 동일 | Windows 실측에서 A안보다 속도·호환성이 좋을 때 선택합니다 |
| C. 조회와 삭제를 `gix`로 처리 | A안 + 브랜치·ref·워크트리 삭제 | 초기에는 네트워크와 아직 검증하지 못한 작업 | A/B안 적용 후에도 삭제 명령 실행이 느릴 때 검토합니다 |

각 안의 근거는 [라이브러리 비교](alternatives.md), 작업 순서는 [전환 계획](migration-plan.md), 비교 조건은 [Windows 측정 계획](windows-benchmark.md)에 정리했습니다.

## Git 명령을 몇 번 실행하나요?

기존 코드는 이미 브랜치·ref 목록을 한꺼번에 조회합니다. 브랜치마다 `rev-parse`를 실행하는 구조는 아닙니다. 반면 정리 직전에는 항목별로 다시 확인하므로 Git 실행 횟수가 많아집니다. 동시 검사는 저장소 사이의 대기를 줄이지만, 저장소 하나의 명령 횟수는 줄이지 않습니다.

로컬에 원격 HEAD 정보가 있고 모든 검사가 성공하는 경우를 코드로 계산하면 다음과 같습니다. Windows에서 측정한 시간은 아닙니다.

| 작업 | 저장소 하나의 Git 실행 횟수 | 관련 코드 |
|---|---|---|
| 검사 | `6 + S`회. `S`는 파일 변경 여부를 검사하는 연결된 워크트리 수 | [planner.rs](../../src/cleanup/planner.rs), [default_branch.rs](../../src/git/default_branch.rs) |
| 정리 | `4 + 3B + 8W + 2C`회. `B`는 단독 브랜치, `W`는 브랜치와 함께 제거하는 워크트리, `C`는 custom ref 수 | [executor.rs](../../src/cleanup/executor.rs) |
| 최신화 | 원격 fetch 외에도 브랜치별 현재 커밋·병합 관계·워크트리·파일 변경을 다시 확인 | [sync.rs](../../src/git/sync.rs) |

검사에서 기준 브랜치를 직접 지정하면 1회 줄고, 원격 HEAD를 네트워크로 질의해야 하면 2회 늘어납니다. 정리 횟수는 로컬 symbolic ref로 기준 브랜치를 판별했고, 중간 오류나 건너뛴 항목이 없는 경우입니다.

예를 들어 워크트리 없이 브랜치 100개와 custom ref 100개를 정리하면 검사는 6회, 정리는 504회입니다. A/B안에서 로컬 조회를 모두 옮기면 검사는 0회, 정리는 삭제·정보 정리 명령만 남아 201회가 됩니다. 라이브러리 미지원으로 Git 명령을 다시 쓰거나 보조 프로그램을 실행하는 경우는 제외한 계산입니다.

실제 시간에는 Git 프로세스 시작 외에도 파일 검사, 압축된 Git 데이터 읽기, 보안 프로그램 검사, 네트워크 대기가 포함됩니다. 실행 횟수 감소를 속도 개선 비율로 해석하지 않습니다.

## 유지할 안전 조건

라이브러리 조회는 아직 도입하지 않았습니다. 적용 전에 `PLAN.md` 18장·24장·부록 A.12와 `AGENTS.md` 6장에 허용 범위를 반영해야 합니다. C안의 삭제 API는 별도 설계와 안전 테스트를 거칩니다.

강제 삭제, 원격 브랜치 삭제, 자동 stash, 워크트리 폴더 직접 삭제, `.git` 파일 직접 수정은 계속 금지합니다. `refs/remote/*`와 `refs/remotes/*` 구분은 기존 `git::refs`를 사용합니다. 기준 브랜치 이름을 추측하거나, 검사 중 저장소를 변경하거나, 삭제 직전 확인을 생략하지 않습니다.

A/B안에서도 Git 설치는 필요합니다. 사용자가 지정한 Git 실행 파일 경로도 그대로 적용합니다. 네트워크·인증까지 라이브러리로 옮기는 것은 별도 검토 대상입니다.
